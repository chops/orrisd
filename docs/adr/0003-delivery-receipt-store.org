* ADR-0003: Serialized delivery receipt authority
:PROPERTIES:
:CUSTOM_ID: adr-0003-serialized-delivery-receipt-authority
:END:
** Decision
:PROPERTIES:
:CUSTOM_ID: decision
:END:
Implement the store portion of the protocol version 2 duplicate/receipt
views pinned by ~test/fixtures/contracts/ipc/v2~. The application starts the store before
its IPC listener and hands it to the listener and panes; that wiring is specified in ADR-0004.

~AiPair.Delivery.ReceiptStore~ is a GenServer. Admission, attempts, transitions,
monitor notifications and journal appends are serialized by that process. Its
public mutation API is ~admit/5~ and ~transition/4~; reconciliation is
~reconcile/5~. It never accepts prompt bytes, only their validated SHA-256 hash.
~observe/2~ is a test observation hook, not a new IPC subscription API.

Admission returns an opaque operation token only for a newly admitted attempt.
Duplicate views contain no such token. A token from a prior attempt is stale;
another message's token, or a fabricated reference, is foreign. Only a terminal
~not_delivered~ attempt can be retried, under the same message ID and a new
attempt number. Receipt identity never changes across attempts.

** Durable Record
:PROPERTIES:
:CUSTOM_ID: durable-record
:END:
The private log is ~delivery/receipts.jsonl~ beneath the configured inbox. Its
directory is narrowed to 0700 and the file to 0600 before any record is written.
Each complete newline-terminated JSON record includes schema/version, sequence,
the exact preceding line's SHA-256 (including newline), daemon epoch, message ID,
pane ID, payload hash, status and delivery attempt. Tokens and owner PIDs are not
persisted. Records are appended, never rewritten to change a prior outcome.

The store uses ~ReceiptLog~ for filesystem and replay work through ~Delivery.Fs~.
Every acknowledged record has completed file fsync. Directory entries are synced
at initialization, not on ordinary appends. There is no mutable head file: boot
reads the complete log and validates its closed shape, chain, gapless sequence,
identity consistency and legal attempt history before making it available.

A record is complete when it is a newline-terminated line, or when it is an
unterminated final tail that decodes as a JSON value. The preceding complete prefix
must validate first. Only a tail that does not decode, or that decodes to an object
with this build's schema and version that also passes full record validation
against the validated prefix, is repairable; that truncation must be synced before
service begins. A complete unterminated tail that fails that validation, lacks a
schema key, or decodes to a non-object is corruption and is refused with the file
unchanged. A complete invalid last record is corruption, not a removable tail.

The S0b build read ~schema_version~ 1 and 2 and wrote only 2 (RS3, below, now writes 3). Version 2 has the same
keys and adds the status ~paste_started~. ~begin_paste~ appends and fsyncs a
~paste_started~ record before it authorizes the paste, so no receipted paste starts
without that durable marker; if the marker cannot be written the store is poisoned,
the caller is told ~receipt_store_unavailable~ and nothing is pasted. Version 2 means
"written by a marker-capable writer": the writer change and the marker landed in one
atomic integration, so no build on main writes version 2 without the marker. While an
attempt is live, ~paste_started~ is internal: replies show the status the attempt had
just before its marker (~pending~ or ~queued~), so every reply is the one it was before
the marker existed. Within one version the version 1 history holds, and ~paste_started~ may
follow only ~pending~ or ~queued~ and be followed only by ~delivered~ or ~ambiguous~,
never ~not_delivered~. Within one attempt the version may change only where boot
finalizes a ~pending~, ~queued~ or ~paste_started~ record as ~ambiguous~; every other
cross-version edge in an attempt is corruption, so no attempt acquires records the
other writer generation would trust. A new attempt (~not_delivered~ then ~pending~
with the next attempt number) may change version. ~paste_started~ in a version 1
line is corruption.

Receipt schema 3 (RS3, NS-15.G.002 B1b). This build reads ~schema_version~ 1, 2 and 3
and writes only 3. A version 3 line has the version 2 keys plus ~registration_id~ and
~generation~, both null or both set (~reg_~ plus 32 lowercase hex; a decimal string): the
registration the pane served when the attempt was admitted. Every line of one attempt
repeats its pair (a pre-3 line reads as null); a new attempt after ~not_delivered~ may
carry a new one. A version 2 attempt continues under version 3 by the version 2 edges;
a version 3 attempt never continues as version 2, boot finalization included. Version 3
adds the terminal status ~cancelled~, legal only after ~queued~: nothing follows it in that
attempt and no new attempt opens. This build reads ~cancelled~ but never writes it; a
stored one reads as ~ambiguous~ in every reply and is never restored. A restored queued
attempt carries its pair into the restore registry and the entry handed to the pane. Only
a protocol version 3 send binds a pair (B1b): the pane identity it proved under the pane's
Coordinator fence is copied into its new attempt at admission (~ReceiptStore.admit/6~, which
requires the binding and refuses one the log could not read back). A version 1 or 2 send
records an explicit null pair, never one inferred from the registry; restored, such an
attempt is unbound and S3 must treat it as unreleasable. A duplicate never rewrites a
stored pair, and a new attempt after ~not_delivered~ takes only its own opener's pair.
Rollback floor: a build before RS3 refuses any version 3 line as
incompatible and leaves the log unchanged, so a rollback after the first RS3 write fails
closed.

A line with another ~schema~ or an unsupported ~schema_version~, newline-terminated
or not, is refused with
~{:receipt_log_incompatible, %{seq: n, found: ..., expected: ...}}~ naming the line,
the found pair and the supported set
~%{schema: "ai-pair/delivery-receipt", schema_versions: [1, 2, 3]}~, and the file is
left unchanged. The classification precedes chain, key-set and history validation, and
a present but unsupported version type is incompatible, not corrupt. Found values
are echoed only when bounded: a schema name matching
~\A[a-z0-9][a-z0-9/._-]{0,63}\z~, else ~:unrecognized~; an integer version in
~0..1_000_000~, else a type marker ~{:unsupported_type, t}~. Recovery is an operator
action: start the daemon build whose receipt schema matches ~found~, or move the
log aside under operator control. This build never repairs or rewrites such a log.
A torn line from another version does not decode and is still repaired as a
fragment; a reader cannot tell it from a torn own line without a format commitment.
Any future receipt schema change must land after this reader has shipped in the
rollback target generation. This chain is not authentication against an attacker
who can rewrite the entire log.

** Ownership and Recovery
:PROPERTIES:
:CUSTOM_ID: ownership-and-recovery
:END:
The store mints its epoch once at initialization and monitors the actual delivery
operation owner, not the requesting connection. Owner loss makes a pending, queued
or ~paste_started~ attempt durably ambiguous. Restart likewise appends ambiguity, before
accepting new calls, for every unresolved prior-epoch pending or ~paste_started~ attempt and
for every queued attempt it cannot restore. A queued attempt stays queued across a restart
only when its epoch is attested in ~delivery/lineage.jsonl~ and its record lies in that
epoch's range, its latest record is a version 2 or 3 queued record with no ~paste_started~
recorded for it, and its exact payload object passes the verified read. A corrupt or
inconsistent lineage file refuses the store unchanged (NS-15.G.003 S2).

A boot-restored queued attempt is owned by the store's restore registry, not by a pane
process: its holder's death returns it to unheld and never finalizes it. A holder fenced for
re-admission or stop is not a death: its tokens are void and the entries pass to the next
admitted holder. The owner-loss rule above still holds for every live attempt.

Reconciliation has exactly five outcomes: delivered, queued, absent, ambiguous,
conflict. ~not_delivered~ is a stored status mapping to absent; it is not a sixth
outcome. A pending live operation may be waited for up to 5 seconds. Timeout does
not append a fabricated outcome: the query answers ambiguous. A subsequent real
completion may still establish delivery. The caller disappearing cancels its
wait, not the operation it was querying.

Any failed append or fsync stops further mutations in that process. Previously
unresolved records cannot then answer queued/pending as if finalization remained
healthy. The caller receives a named error and must recover the store; the code
does not append behind an uncertain tail. A failed first admission may still be
queried as absent because that operation was never authorized to paste.

** Crossing the Paste Boundary
:PROPERTIES:
:CUSTOM_ID: crossing-the-paste-boundary
:END:
~begin_paste/3~ authenticates the current operation token immediately before the
pane invokes the physical paste. It grants that permission once per attempt,
appends and fsyncs a version 2 ~paste_started~ record before replying ~:ok~, and
marks the attempt in flight in memory together with its pre-marker status. That
durable marker is the crash evidence that a paste may have begun; a crash before it
leaves the pending or queued record, which boot also finalizes as ambiguous. A
failed marker write poisons the store and authorizes nothing. A queued attempt in
flight uses the pending bounded-wait behavior, not an immediate queued answer, and
its replies still show ~queued~. Terminal finalization removes the runtime mark; owner loss wakes
waiters with durably recorded ambiguity. Once paste is authorized, neither
~not_delivered~ nor a return to ~queued~ is accepted from that token.

This extends the component for its pane-wiring obligation; IPC and pane callers
must use it before the side effect. The ~paste_started~ record proves only that
a paste may have begun, never that it completed; it is never projected on the wire
and never restored as queued.

** Scope Limits
:PROPERTIES:
:CUSTOM_ID: scope-limits
:END:
- Single ownership is enforced for a normalized inbox path within this BEAM.
  The enclosing host must ensure only one daemon opens the inbox. This is not a
  cross-VM filesystem lock or a canonical-inode alias arbiter.
- The configured inbox and its filesystem namespace are host-owned. This design
  does not claim protection from concurrent same-user path replacement.
- Durability uses the existing seam's ~fsync~, not macOS ~F_FULLFSYNC~; it does
  not claim survival of every device-cache or sudden-power-loss failure.
- Supervision ordering and pane receipt wiring are specified in ADR-0004, not here.
- A graceful close failure is logged by name; no new public shutdown command is
  introduced. Initialization cleanup errors preserve both failure reasons.

** Verification
:PROPERTIES:
:CUSTOM_ID: verification
:END:
The store is covered by ~test/ai_pair/delivery/receipt_store_test.exs~. The
gapless-admission test uses a long-lived operation owner: short-lived
concurrent tasks otherwise legitimately emit owner-loss records beyond the 24
admissions being counted. No expected receipt transition was removed.

Additional regressions cover mutation refusal after uncertain writes, truthful
query rejection after uncertain finalization, malformed filesystem results,
strict ID/hash grammars, duplicate-token nondisclosure, complete-tail corruption,
and an invalid attempt history despite valid hash links.
~test/ai_pair/delivery/receipt_log_compatibility_test.exs~ covers complete
unterminated tails (repairable only when valid and own-version, refused otherwise
with the bytes unchanged and no truncation) and the incompatible-version term with
its bounded found values. The canonical gate is
~nix develop --impure --command bin/verify~.

Operators explicitly choose when to deploy a new package. An older daemon cannot use these receipts to authorize sends;
the caller must fail closed when delivery reconciliation is unavailable.
