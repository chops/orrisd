* Durable-mode configuration contract
:PROPERTIES:
:CUSTOM_ID: durable-mode-configuration-contract
:END:
This document freezes the six ~:ai_pair~ application-environment keys that switch
the daemon from its legacy composition to the durable one, the supervision order
the durable branch requires and why each edge exists, the rules that make a
durable boot fail closed, and the guarantee that with durability off the legacy
composition is unchanged. The tables under
~test/fixtures/contracts/durable-mode-config~ are pinned byte-for-byte by
~test/ai_pair/contracts/durable_mode_configuration_test.exs~.

The behaviour is the R04 S10 slice's (audit
R04-BOOT-RESTORATION-SOURCE-GAP-AUDIT section 4, row S10, flagged
CONTRACT-CHANGE; it is the last of that audit's four CONTRACT-CHANGE
prerequisites). The producer is not on main: main's
~lib/ai_pair/application.ex~ has no durable branch, reads none of these six keys
and starts exactly the eight legacy children (~main:27-36~). Three of the six
already have a reader on main — ~AiPair.IPC.Server~ reads
~:durable_attachments~, ~:project_binding~ and ~:tmux_server~ once S9 landed —
and three (~:pane_intent_store_fs~, ~:pane_intent_store_module~,
~:boot_generation~ as an environment key) have no reader at all until S10.

*Enabling any of these keys in the installed configuration, and restarting the
installed daemon, are reserved to Charles.* See "Installed activation".

** The one switch
:PROPERTIES:
:CUSTOM_ID: the-switch
:END:
Durable mode is ~Application.get_env(:ai_pair, :durable_attachments) == true~, a
literal ~true~ and nothing else (~lane:42~; ~server.ex:741~; ~scope:40-44~).
Everything else in this document is conditional on that one comparison.

The comparison is made in two places with two different lifetimes, and the
difference is contractual:

- ~AiPair.Application.start/2~ reads it ONCE, while building the child list
  (~lane:41-43~). The supervision tree a daemon runs is therefore decided at
  boot and never changes.
- ~AiPair.IPC.Server~ re-reads it for every dispatch (~server.ex:741~; the
  durable attach/detach contract, "The mode gate"), so the request path can be
  switched off on a running daemon.

A daemon started legacy and then given ~:durable_attachments = true~ at runtime
therefore has a durable REQUEST path with no Coordinator, no store and no boot
generation. Its ~IPC.Server~ was constructed with ~boot_generation: nil~
(~server.ex:1017~), so every durable attach answers ~durable_unavailable~ and
every legacy-shaped attach and detach answers ~coordinator_unavailable~ (C1
~RED:3860-3891~). Nothing is corrupted and nothing is silently degraded, but the
daemon serves refusals until it is restarted. Durability is a restart-scoped
deployment decision, not a runtime toggle.

**** The ~fetch_env~ rule
Absence and a present-but-useless value are distinguished with
~Application.fetch_env(:ai_pair, :boot_generation)~: ~:error~ means mint,
~{:ok, value}~ means validate and fail closed if the value is not a decimal
string (~lane:62-68~; ~scope:175~). The r8 proposal text spelled this
~Application.get_env(...) || Marker.mint_generation()~ (~scope:210-211~); the
ruling at ~scope:175~ governs, as ~scope:186-187~ states. The difference is
observable: under ~get_env || mint~, an explicit ~nil~ or ~false~ would SILENTLY
mint, whereas under ~fetch_env~ it is a present value that fails the decimal
check and fails the boot. A configuration that names the key must name a usable
value.

**** What the generation is for
The one validated value is passed to ~AiPair.IPC.Server~ as ~boot_generation:~
(~lane:103~), which validates it again in durable mode (~server.ex:1013-1021~)
and uses it for exactly one thing: the generation OFFERED to ~Marker.ensure~ when
a pane's session marker is absent (~server.ex:1136-1139~; ~scope:57-59~). The
value actually recorded is always the one read back from the marker
(~server.ex:1149~; ~scope:57-60~). Boot reconciliation consumes existing markers
and mints nothing: a durable boot over live marker-less sessions performs zero
marker writes (~reconciler.ex:64~; B2 ~RED:1959~; G9 ~RED:3599~).

The value is immutable for the life of the daemon and survives an ordinary
restart of the ~IPC.Server~ child, because it was computed by ~Application~ and
lives in that child's spec (~lane:103~; ~scope:176~).

*** The inbox root is not one of these keys
Every durable key is relative to the daemon inbox, which is resolved exactly as
it is today by ~AiPair.Inbox.resolve!/0~ (~main:19~; ~lane:19~) from
~:ai_pair, :inbox~, then ~AI_PAIR_INBOX~, then the default path (~main:50-54~).
S10 changes nothing about that resolution. The inbox is the store child's
~root:~, the ~Path.expand~ input to the store's ~:global~ key, ~Boot~'s ~root:~
and therefore the boot report's directory (~lane:74,77,100~; ~boot.ex:191~).

** Supervision order
:PROPERTIES:
:CUSTOM_ID: supervision-order
:END:
Both branches use ~Supervisor.start_link(children, strategy: :one_for_one, name:
AiPair.Supervisor)~ (~main:38-39~; ~lane:29-30~), so children are started in list
order and each child's ~start_link~ returns before the next one begins. The
frozen tables are
~test/fixtures/contracts/durable-mode-config/supervision.legacy.json~ and
~supervision.durable.json~.

*** Before any child: the generation
The generation is fetched, minted if absent and validated BEFORE the child list
is built (~lane:61-68~). A rejected ~:boot_generation~ therefore raises with no
child started, no supervisor, no socket and no marker write ATTEMPTED — which is
what G9 measures, counting marker argv through an external wrapper
(~RED:3654-3663~). Validating it later, for instance only inside
~IPC.Server.start_link/1~ where main already validates it (~server.ex:1019~),
would let a whole reconciliation run and quarantine panes before the daemon
failed.

**** The ~Boot~-before-~IPC.Server~ edge
This is the load-bearing one and the only one the RED measures directly. Because
a static ~:one_for_one~ supervisor starts children sequentially and ~Boot~ is
ready on return, the listen socket is not created until reconciliation is done.
B5b holds the boot-time ~:list~ and asserts that while it is held
~AiPair.Supervisor~ is alive, ~AiPair.IPC.Server~ is NOT registered, nothing
accepts on the socket path, and the socket FILE does not exist
(~RED:2412-2422~); after the release the whole composition is present and ~ping~
answers (~RED:2429-2432~).

What breaks if ~IPC.Server~ starts first: a client attach could reach the daemon
while the boot's single reconciliation is still running. The per-pane fence
keeps that from corrupting anything — one of the two takes the pane and the
other is refused ~pane_busy~ — but the outcome becomes timing-dependent: a pane
a user just attached could be observed and quarantined by the same boot's
reconciliation, or a pane reconciliation is about to quarantine could be refused
to the user for reasons that describe a boot they cannot see. The rule is
therefore stronger than "no corruption": no client may reach the daemon before
the boot's one reconciliation attempt has settled.

**** What ~Boot~ does NOT delay
The deadline bounds the WAIT, not the work. A coordinator-owned effect worker
accepted inside a fence is never terminated by ~Boot~; it outlives the deadline
and keeps its pane fenced until its reply arrives, and the already-published
report is not rewritten (~boot.ex:32-35,296-314~; B12b ~RED:2815-2818~;
~scope:80-84~). So ~IPC.Server~ can start while an effect from reconciliation is
still outstanding, and an attach on that pane is correctly refused
~unresolved_operation~ until it settles.

*** The connection cap
:PROPERTIES:
:CUSTOM_ID: connection-cap
:END:
One option has been amended since the freeze above, on 2026-09-19, and it is
recorded here rather than left as a fixture diff.

Child 6 of the legacy list, and child 9 of the durable one, gained
~max_children: max_connections~, where ~max_connections~ is
~AiPair.IPC.Server.max_concurrent_connections/0~. Before the amendment
~AiPair.IPC.ConnectionSupervisor~ was a bare ~Task.Supervisor~ with no bound,
which is threat T-22 of ~phase0/mcp-threat-model.org~ in the planning
repository: a local process opening connections in a loop without sending a
frame held one handler task and one socket each, for
~AiPair.IPC.Server~'s five-second handler receive timeout, with nothing
refusing the next one.

- What the cap does :: the bound is enforced inside the supervisor, so
  ~Task.Supervisor.start_child/2~ answers ~{:error, :max_children}~ for a
  connection beyond it. ~AiPair.IPC.Server~'s acceptor already treats a failed
  spawn as a closed client socket and resumes accepting, so the surplus
  connection is REFUSED, not queued and not deferred.
- Who owns the number :: ~AiPair.IPC.Server~, beside that surface's frame and
  payload bounds, exposed as ~max_concurrent_connections/0~. The composition
  calls the accessor; the literal exists in one place, as
  ~AiPair.Pane.StateMachine.max_pending_sends/0~ does for the per-pane send
  queue.
- What the number is :: the same literal as ~@max_pending_sends~, this
  repository's only other count bound. Every legitimate connection carries one
  command and is gone as soon as it is answered, so the cap bites only on
  connections left open and idle.
- What it does NOT do :: it does not authenticate anybody, and it does not stop
  a local process from taking the whole cap for the handler timeout and making
  the daemon refuse a legitimate connection for that window. It converts an
  unbounded resource into a bounded and self-clearing one. The residual is
  stated rather than closed, because a cap that silently made the daemon
  unavailable would be worse than the growth it replaced.
- Read by ::
  ~test/ai_pair/ipc/connection_cap_test.exs~ takes the cap concurrently and
  measures the refusal, so the bound is a statement that can fail.

** Installed activation
:PROPERTIES:
:CUSTOM_ID: installed-activation
:END:
*Setting any of these six keys in the installed daemon's configuration, and
restarting the installed ~ai-pair~ daemon, are reserved to Charles. No slice
performs either, and this contract authorises neither.*

- Enabling ~:durable_attachments~, supplying ~:project_binding~, or setting any
  other key of this contract in the installed configuration — through
  home-manager, launchd, a release ~config/runtime.exs~ or any other installed
  path — is an ACTIVATION step, not an implementation step. The audit lists it as
  reserved (R04-BOOT-RESTORATION-SOURCE-GAP-AUDIT section 5, first entry).
- Restarting the installed daemon so a configuration change takes effect is
  equally reserved, and it is the ONLY way any of these keys takes effect: the
  supervision tree is decided once per boot (~lane:42~).
- The register's ~installed_live_compatibility~ class is HELD for NS-15.G.001,
  NS-15.G.002 and NS-16.*; nothing here changes that, and S10 landing does not
  close any of those controls.
- The four keys ~:tmux_server~, ~:pane_intent_store_fs~,
  ~:pane_intent_store_module~ and ~:boot_generation~ exist so that tests can
  substitute a fixture adapter, a fault-injecting filesystem, a controlled store
  and a pinned generation (~RED:1997,2376,3583-3584~). They are test seams. An
  installed daemon setting any of them is outside this contract.
- A durable boot performs real effects on the operator's machine: it takes a tmux
  census, reads session options, starts quarantined pane children for recorded
  intent and writes ~<inbox>/state/boot-report.json~. That is why activation is
  reserved and why the RED runs against private fixture tmux servers rather than
  the operator's (~scope:246~).

** Open questions for the S10 review
:PROPERTIES:
:CUSTOM_ID: open-questions
:END:
- OQ-1 a binding whose ~project_inbox~ is not the resolved inbox. The store is
  registered under the INBOX (~lane:77~) while durable attach resolves the store
  under the BINDING's ~project_inbox~ (~server.ex:815~), so the two disagree
  silently and every durable attach answers ~durable_unavailable~ while
  reconciliation works. Should S10 refuse such a configuration at boot — the
  daemon can compare the two values before starting anything — or is
  ~durable_unavailable~ the honest answer? No RED row covers it. Refusing at boot
  would be a fail-closed rule this contract does not currently state.
- OQ-2 an unregistered ~:pane_intent_store_module~. ~scope:197-199~ makes global
  registration a REQUIREMENT of the configured module but nothing checks it, and
  the failure surfaces much later as ~{:source_unavailable, :intent}~ plus
  ~durable_unavailable~. Should S10 verify the ~:global~ key is claimed after the
  store child starts, and fail closed if it is not?
- OQ-3 the Coordinator's fail-closed rule has no RED row. ~scope:70~ requires
  that a durable store OR coordinator child start failure fails boot closed, and
  B5a measures only the store (~RED:1981~). The Coordinator's ~start_link/1~ can
  answer ~{:error, {:unknown_options, keys}}~ (~coordinator.ex:58-59~), which is
  the only non-crash failure it has, and S10 passes ~[]~ (~lane:98~), so the case
  may be unreachable in practice. Recorded rather than asserted.
- OQ-4 no key controls the reconciliation deadline. ~Boot~'s ~deadline_ms~
  defaults to 10000 (~boot.ex:72~) and the lane never passes one (~lane:100~), so
  an installed daemon with a large store has no way to widen it and B12a's
  timeout path would fire in production with no operator control. Should S10 add
  a seventh key, or is a fixed 10 s deadline the contract?
- OQ-5 ~:project_binding~ has no default and no derivation. The lane reads it and
  passes it through even when ~nil~ (~lane:71,100~). A daemon whose inbox is
  known could derive ~project_inbox~ from it, but ~scope:74-77~ forbids deriving
  the binding from records and says nothing about deriving it from the inbox.
  Left undecided.
- OQ-6 the durable branch duplicates the seven shared children literally
  (~lane:93-97,101-102~ versus ~lane:46-53~). Nothing keeps the two lists in
  step, and a change to a shared child made in one branch only is exactly the
  silent divergence the legacy claim forbids. Whether S10 should build the
  durable list by SPLICING into the legacy one, rather than restating it, is a
  structural question the review should settle; this contract's test pins the
  legacy list precisely because the lane's shape makes divergence easy.
