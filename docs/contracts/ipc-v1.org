* ai-pair IPC contract v1
:PROPERTIES:
:CUSTOM_ID: ai-pair-ipc-contract-v1
:END:
This document describes the IPC v1 reply shapes this daemon produces. The
fixtures under ~test/fixtures/contracts/ipc/v1~ are shared byte-for-byte with
the Orris consumer. This v1 contract does not add fields to the wire.

** Framing and version
:PROPERTIES:
:CUSTOM_ID: framing-and-version
:END:
- Transport is a local Unix-domain socket using four-byte length-prefixed JSON
  frames.
- ~protocol_version~ is implicitly ~1~ and is absent from v1 requests and
  replies.
- A ~send~ request may carry ~msg_id~. The daemon uses it for delivery and
  telemetry correlation but does not echo it in a v1 reply.
- Strings of the form ~<name>~ in fixtures are dynamic placeholders. Tests must
  replace only documented dynamic fields before comparing decoded objects.
- ~pane_status.state~ is one of ~idle~, ~busy~, ~dialog~, ~dead~, or ~unknown~.
- ~pane_status.agent~ is a registered agent string or ~null~.
- ~pane_status.classifier~ is a classifier name string.
- ~pane_status.pending_count~ is a non-negative integer; the fixture's ~0~ is a
  representative value, not a fixed constant.
- A queued send has ~queue_reason~ equal to ~debounce~, ~busy~, ~dialog~, or
  ~unknown~.

** Reply fixtures
:PROPERTIES:
:CUSTOM_ID: reply-fixtures
:END:
| Fixture                                  | Meaning                                                                                    |
|------------------------------------------+--------------------------------------------------------------------------------------------|
| ~ping.ok.json~                           | Daemon is reachable; ~<version>~ is the running ai-pair version.                           |
| ~pane_status.ok.json~                    | Pane is registered; ~<pane_id>~, ~<state>~, ~<agent>~, and ~<classifier>~ are dynamic.     |
| ~pane_status.error.missing_pane_id.json~ | Request omitted a usable pane ID.                                                          |
| ~pane_status.error.pane_not_found.json~  | No live registered state machine owns the pane ID.                                         |
| ~pane_status.error.pane_dead.json~       | The pane owner died between lookup and status observation.                                 |
| ~send.sent.json~                         | Text was pasted synchronously.                                                             |
| ~send.queued.json~                       | Text entered the live pane state machine's bounded in-memory queue but was not pasted yet. |
| ~send.error.missing_pane_id.json~        | Request omitted a usable pane ID.                                                          |
| ~send.error.pane_not_found.json~         | No live registered state machine owns the pane ID.                                         |
| ~send.error.queue_full.json~             | The bounded pending-send queue is at its v1 cap of 32.                                     |
| ~send.error.missing_text.json~           | Request omitted a string payload.                                                          |
| ~send.error.oversize.json~               | Payload exceeds the v1 cap of 524288 bytes.                                                |
| ~send.error.pane_dead.json~              | The registered pane state machine is terminal.                                             |
| ~send.error.send_timeout.json~           | The pane state machine missed the configured call deadline; ~<detail>~ is diagnostic text. |
| ~send.error.paste_failed.json~           | Synchronous tmux paste failed; ~<detail>~ is diagnostic text and is not machine-readable.  |

~queued~ and ~queue_full~ are typed outcomes, not transport failures. Consumers
must preserve the distinction. Consumer behavior for each outcome after protocol
negotiation is defined by the consumer's own contract.

Malformed JSON and unknown commands are framing/command-dispatch errors outside
this consumer fixture set. They remain daemon behavior but are not pane-delivery
outcomes.

** Hash
:PROPERTIES:
:CUSTOM_ID: hash
:END:
This repository pins the JSON files and ~CONTRACT_HASH~ (the Orris consumer
pins the same bytes). The hash is lowercase SHA-256 over this byte sequence:

1. Select only ~*.json~ files in this directory.
2. Sort their relative filenames by byte value.
3. For each file, append ~filename~, one NUL byte, exact file bytes, and one NUL
   byte.
4. Hash the concatenation and store the 64 hexadecimal characters plus a final
   newline in ~CONTRACT_HASH~.

The documentation file and ~CONTRACT_HASH~ itself are not hash inputs.

*** What the v1 difference actually is, measured 2026-09-19
:PROPERTIES:
:CUSTOM_ID: v1-document-difference
:END:
Recorded here rather than left as a bare hash mismatch. Measured with ~diff -u~
of this file against ~docs/contracts/ipc-v1.org~ at orris
~3684f53e~ (that copy digests to
~485b0ec8ae851b104a03b7dbf5d4c5dc6c10da5400adb2aea695505fff08b545~). The two
texts differ in five places and agree everywhere else -- the whole "Framing and
version" list, the whole fifteen-row fixture table and all four steps of the
hash rule are byte-identical:

1. Opening. This copy says the reply shapes are the ones "this daemon
   produces". The consumer copy opens with an "Implementation status" section
   naming ~AiOrchestrator.Dispatch.PaneClient~, ~lib/ai_orchestrator/dispatch/pane_client.ex~
   and ~test/dispatch/pane_client_contract_test.exs~. Each statement is true of
   the repository that makes it and false of the other.
2. The ~queued~ / ~queue_full~ closing sentence. Here: consumer behaviour "is
   defined by the consumer's own contract". There: "A later revision defines
   consumer behavior for each outcome (see ~ipc-v2.org~)". Same fact, two
   wordings.
3. The first sentence of "Hash". Here it notes that the Orris consumer pins the
   same bytes; there it names the fixture directory. The RULE itself is
   identical, which resolves the earlier open question about whether only one
   copy stated it.
4. This "Paired revision" section exists only here. It is a producer statement
   about the consumer, and could not be adopted by the consumer unchanged.
5. "Planned protocol version 2 changes". Here v2 is described as implementing
   explicit ~protocol_version~, capability advertisement, ~msg_id~ echo and
   incompatible-peer rejection, with subscription reserved. There they are
   "targets, not v1 facts" that "require a contract revision and fixtures
   before implementation". Version 2 IS delivered on both sides -- the vendored
   consumer text in [[./ipc-v2.org][the version 2 contract]] opens with "The
   consumer side of this contract is delivered" -- so the consumer wording is
   the one that is behind. Both agree subscription is not in v2.

CLASSIFICATION: this is not one document lagging the other, and neither may be
adopted wholesale. Differences 1 and 4 are repository-specific facts that would
become FALSE statements if copied across; difference 5 is a real staleness, and
it is in the OTHER repository, which this repository cannot fix. Differences 2
and 3 are equivalent restatements with no disagreement in them.

DECISION OWED, and deliberately not taken here: whether v1 should be restructured
the way v2 was -- one authored text vendored verbatim with each repository's
own statements outside a digested region -- and if so which repository authors
it. That is a reviewed change in BOTH repositories, so a single-repository lane
cannot make it; picking a winner unilaterally would delete true statements from
one side. Until it is taken, the two v1 documents remain different texts and
the fixtures, their ~CONTRACT_HASH~ and the hash rule remain the shared,
verifiable part.

** Planned protocol version 2 changes
:PROPERTIES:
:CUSTOM_ID: planned-protocol-version-2-changes
:END:
Protocol version 2 implements explicit ~protocol_version~, capability
advertisement, ~msg_id~ echo, and incompatible-peer rejection; see
[[../adr/0004-versioned-delivery-wiring.org][the versioned delivery design]] and
~test/fixtures/contracts/ipc/v2~. These are not v1 fields. Subscription is
reserved for future work and requires its own contract and fixtures.
